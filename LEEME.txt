PAQUETE DE TELEMETRIA LORA

Contenido
- radio_node.ino: firmware para ATmega328P + RFM95.
- heltec_estacion.ino: firmware de estacion Heltec WiFi LoRa 32 V3.
- interfaz_telemetria.py: interfaz de escritorio existente.
- simular_protocolo.py: pruebas logicas reproducibles sin hardware.

Carga
1. Abrir radio_node.ino como sketch Arduino. Si el IDE lo solicita, crear una
   carpeta radio_node y colocar dentro el archivo con ese mismo nombre. Cargarlo
   al ATmega328P usando el programador, seleccionando placa y clock correctos.
   El monitor serie del nodo funciona a 9600 baudios.
2. Abrir heltec_estacion.ino como sketch Arduino. Si el IDE lo solicita, crear
   una carpeta heltec_estacion y colocar dentro el archivo con ese mismo nombre.
   Cargarlo a la Heltec WiFi LoRa 32 V3. El monitor serie trabaja a 115200
   baudios. La interfaz Python abre ese puerto serie.
3. Iniciar interfaz_telemetria.py con Python y seleccionar el puerto COM de
la Heltec. La interfaz requiere pyserial y tkinter (normalmente incluido con
Python). Los graficos se dibujan con tkinter; matplotlib no es necesario.

Comandos remotos desde la interfaz/Heltec
- S0 a S180: posicion del SG90 estandar (0° a 180°); al arrancar queda en 90°.
- Switch entre D5 y GND: después de armar con CDA, debe detectarse cerrado y
  luego abrirse estable durante 2 s para mover el servo a 180°. Un D5 flotante
  o desconectado no lo acciona. Una activación por cada CDA.
- CDA en la interfaz arma el accionamiento automático; DESARME lo bloquea y
  queda enclavado aunque se vuelva a pulsar CDA. REARME libera el bloqueo.
  DESARME no bloquea los comandos manuales S0..S180. Al reiniciar, queda desarmado.
- FLOOR: fija como cero la ultima altura BMP recibida.
- BZ: alterna el buzzer activo HYDZ conectado a D3 y GND del nodo (apagado al iniciar).

Los controles DHT/BMP/GY y Mostrar todos/Ocultar todos de la interfaz solo
muestran u ocultan paneles localmente; no envian comandos de radio.
El nodo intenta transmitir cada 200 ms (hasta 5 paquetes por segundo).
Para evitar colisiones, la Heltec solo transmite comandos despues de cada quinto
paquete de telemetria (ventana de subida, aproximadamente una vez por segundo).
El nodo reserva hasta 400 ms despues de ese paquete para recibir el comando;
esto puede reducir ligeramente la cadencia efectiva durante ese intervalo.
La Heltec envia tres copias con la misma secuencia por ventana y reintenta en
hasta ocho ventanas; el nodo deduplica la secuencia para que comandos toggle
como BZ solo se ejecuten una vez.
La confirmacion vuelve incluida en el siguiente paquete normal; no se envia una
respuesta LoRa adicional. Esto conserva la cadencia de telemetria y limita los
comandos a una frecuencia adecuada para controles y cambios de sensores.
El DHT11 se consulta cada 2 s y se repite su ultima lectura en los paquetes
intermedios; el BMP se consulta cada 1 s. El acelerometro se lee en cada ciclo.

Diagnostico del BMP180
El nodo imprime “Aviso: no se encuentra el BMP180” si bmp.begin() falla y
manda B=E en la telemetria. En ese caso no es un fallo de formato LoRa:
verificar SDA=A4, SCL=A5, 3V3 y GND en el nodo y comprobar que el sensor sea
BMP180 (direccion I2C 0x77). No conectar el BMP a los pines I2C de la Heltec;
el sensor pertenece al nodo ATmega.

Pruebas realizadas
Desde esta carpeta, ejecutar: python simular_protocolo.py
La simulacion comprueba la coincidencia de parametros de radio, lectura de
paquetes, sensores con error, controles locales, zona muerta del acelerometro,
formato y confirmacion de comandos. No sustituye compilacion Arduino ni prueba
de radio/sensores reales. Arduino CLI no esta instalado en el entorno de QA.

Radio: ambos lados configurados para 915 MHz, BW 125 kHz, SF7, CR 4/5,
sync word 0x12 y CRC. Asegurar que la frecuencia sea la permitida en la zona
y que cada modulo use antena adecuada antes de transmitir.
